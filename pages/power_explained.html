Power Dashboard — Explained

What each tile on /power shows, the exact formula or threshold behind it, and the assumptions that went into each one. Written for whoever (including future-me) needs to tweak a threshold later.

Overview

/power is a read-only monitoring page: it polls the robot's PWR sentence every 3 seconds (same transport as STA on /control, documented on the Protocol page) and never sends a command that changes robot state. The dashboard has five groups: Net power balance (top-left), Solar / PV array, Battery, Load output, and Temperatures (bottom-right — battery, controller, and Pi #1's own CPU, grouped together as vertical bars). All the "is this value okay?" tiles (state of charge, battery voltage, the three temperatures) use the same segmented status-color bar; the pure flow readings (PV and load voltage/current/power) use a plain value with a rolling sparkline instead, since there's no natural "good/bad" zone for those. Below the live dashboard, a History section (see its own section further down) trends battery charge over a rolling day and month, backed by a small database on Pi #1.

Status color scale

Every segmented gauge on the page is colored with the same four-step scale, in the same order, so a color always means the same thing wherever it appears:

  • good — #0ca30c
  • warning — #fab219
  • serious — #ec835a
  • critical — #d03b3b

The zones run in opposite directions depending on which way danger points: for state of charge and battery voltage, a low value is the problem (a draining battery), so critical sits at the bottom of the scale and good at the top — a "falling danger" gauge. For battery temperature and controller temperature, a high value is the problem (overheating), so the order is flipped — a "rising danger" gauge. Mixing these up silently paints a normal reading red or a dangerous one green, so every gauge on the page is explicit about which direction it uses (see the thresholds table below).

Net power balance

net_power_W = pv_power - load_power

The semi-circular dial reads 0 W at its apex. A positive value (production greater than draw) fills the right arm in green and reads "Storing"; a negative value fills the left arm in red and reads "Consuming". The scale is fixed at ±100 W (confirmed against this robot's actual panel/load sizing).

Assumption: this formula only gives the real "is the battery charging or draining" number if the robot's own electronics are wired through the Tracer controller's LOAD output (its switched, protected output) rather than straight off the battery bus. That's the wiring this robot uses, so load_power is the right "consumption" term here.

Time until empty

Shown under the dial only while in the "Consuming" state (discharging). Hidden the moment the balance turns positive or zero.

discharge_current_A = abs(net_power_W) / battery_voltage remaining_capacity_Ah = (battery_soc / 100) * 35 # 35Ah battery, user-confirmed minutes_until_empty = remaining_capacity_Ah / discharge_current_A * 60

This is a simple instantaneous estimate: it assumes the current draw stays exactly where it is right now for the rest of the discharge, and it doesn't model the battery's real discharge curve or the Peukert effect (a battery drained faster delivers less total capacity than its nameplate Ah rating). Good enough as a rough heads-up ("you've got about 40 minutes"), not a precision fuel gauge. Hidden entirely when the draw is negligible (<10 mA) to avoid displaying an absurdly large number.

State of charge (SOC)

SOC is a percentage estimate of how much usable energy is left in the battery relative to a full charge: 100% means fully charged, 0% means the controller considers it fully discharged (its configured low-voltage disconnect point) — not a direct physical measurement, since a battery has no native "percentage" signal to read.

The Tracer charge controller computes this value internally and the robot simply reads it over Modbus, in the same real-time data block as the PV/load/battery readings (one poll covers all of them, via TracerReader) — battery_soc is not something link/tracer_reader.py calculates itself.

Caveat worth knowing: on this class of MPPT controller, that internal estimate is primarily voltage-based, calibrated against the battery type/capacity configured in the Tracer's own settings (battery type, nominal voltage, voltage thresholds) rather than true coulomb counting. A heavy, brief load causes voltage sag, which can make the reported SOC dip and recover a few points even though the battery's actual remaining capacity barely moved. Treat a single SOC reading taken right after the motors pull current with a bit of caution; the trend over several readings is more trustworthy than any one instant value — which is also why the dashboard's thresholds (25/50/75%, see below) are read straight off this same controller-reported field rather than recomputed independently.

CPU temperature (Pi #1) implemented 2026-10-05

Pi #1's own CPU temperature is now shown alongside the battery and controller temperatures, grouped together in a single "Temperatures" panel at the bottom-right of the page — drawn as a vertical (thermometer-style) bar, the layout chosen after comparing it against a horizontal-bars alternative.

How it's read

link/cpu_temp.py (robot repo) reads /sys/class/thermal/thermal_zone0/temp directly — a plain kernel sysfs file, present on every Linux box with a thermal zone, no subprocess and no extra package. It holds the temperature in millidegrees Celsius as plain text (e.g. 47800 → divide by 1000 for 47.8°C). Chosen over shelling out to vcgencmd measure_temp (needs the vcgencmd binary and spawns a subprocess on every read). No background thread, unlike TracerReader: a single sysfs read is cheap enough to do fresh on every PWR request, inside RobotState.power_status().

Thresholds unconfirmed

Based on Raspberry Pi's own thermal throttling behaviour (soft throttling kicks in around 80–85°C on recent Pi boards): good below 60°C, warning 60–70°C, serious 70–80°C, critical at 80°C and above (throttling risk) — same "rising danger" direction as the other two temperature gauges. These are a reasoned starting point, not yet measured against this robot's actual enclosure/airflow; adjust the breaks array in power.html's cpuTemp gauge once real readings are in.

Where the data travels

Added as a 13th field to the existing PWR sentence response (cpu_temp), appended after controller_temp and before the trailing availability flag — no new sentence type, extend-only (same evolution rule as the rest of the protocol, see Protocol). Important distinction: that trailing flag reflects the Tracer's own availability (RS485 cable connected and answering) — cpu_temp does not depend on it and is still reported even when the Tracer is unplugged, since nothing about reading Pi #1's own CPU requires the Tracer to be present.

History — battery charge implemented 2026-10-05

Below the live dashboard, two full-width charts trend the battery's state of charge over a rolling day (last 24h) and a rolling month (last 30 days), one sample every 5 minutes. "Rolling" means always full and up to date — not a calendar day/month that resets at midnight or the 1st and sits mostly empty right after.

Where the data lives

A new SQLite database on Pi #1 (link/power_history.py, table power_log), written by a background logger in the robot's own control server process — not on Pi #2/robot-webserver. This was a deliberate choice: Pi #1 keeps logging even if the WiFi link between the two Pis is briefly down, since the logger reads straight off its own in-process robot state rather than going over the network. The trade-off is that fetching a chart's data from Pi #2 needs a round trip to Pi #1 (see below), rather than a local read.

Logging is gated on the Tracer, not on a timer

A row is only written when PWR's own availability flag is true — i.e. the RS485/Tracer link is actually answering right now. Logging unconditionally every 5 minutes would otherwise fill the history with rows of placeholder zeros every time the cable is unplugged. If the chart above is empty, the most likely reason is simply that the Tracer hasn't reported data yet since the logger started.

Retention

Rows older than POWER_LOG_RETENTION_DAYS (default 395 days, about 13 months) are pruned automatically after every write. At one sample every 5 minutes that's roughly 288 rows/day, ~8,640/month, ~105,000/year — on the order of 1.3 MB/month, so the default window was set generously (a full year plus margin, for season-over-season comparison) rather than tightly, since storage was never the binding constraint here.

Getting data from Pi #1 to the chart

A new HIS sentence (see Protocol) lets Pi #2 ask Pi #1 for a page of the day/month window: HIS,<DAY|MONTH>,<offset> in, a count plus up to 100 rows out. It's paginated rather than returning a whole month (~8,640 rows) in one line — power_history_client.py on Pi #2 loops over pages until it has the full window, and Flask's new GET /api/power_history?period=day|month endpoint (used by this page's own polling, every 5 minutes) hands the assembled rows back as JSON.

Scope of this first version battery charge only

Every other PWR indicator (PV/battery/load voltages, currents, powers, both temperatures, plus Pi #1's own CPU temperature) is already being logged in the same database row — it's simply not charted yet. The user explicitly scoped the first version of these two charts to battery charge only; adding another chart later is a frontend-only change, no backend or database change needed. GPS position is also logged per sample (nullable, when there's no fix) but deliberately not charted here either, by explicit choice — a lat/lon pair isn't naturally a time series.

Snapshot geotagging implemented 2026-10-05

Separately, every CAM,SNAP camera snapshot is now recorded in the same database (table snapshots): filename plus whatever GPS fix was live the moment the photo was taken (NULL/NULL if there was no fix yet). This isn't gated on the Tracer at all — it has nothing to do with the solar charge controller — and isn't surfaced on this page yet either; it exists so a future view can answer "where was this photo taken" without re-deriving it after the fact.
