Web Server Architecture

Overview of the robot-webserver project files (Raspberry Pi #2) and their dependencies, both on the code side and the network side. This page describes the web app; see the control protocol for details on the frames exchanged with the robot.

Robot-side motor/gamepad architecture (Pi #1, for context)

The "GPS Driving" button (was labeled "GPS route" before 2026-09-12) on /control sends an RTE frame to Pi #1 (see the protocol page). The robot repo is documented separately, but since this diagram explains what actually happens once that frame (or any other command) arrives there, it's kept here for context. Full detail — including the honesty notes on what's real versus not-yet-implemented — lives in that repo's own README, section "Pilotage moteur et manette".

Raspberry Pi #1 — "robot" repo, single Python process (python3 -m link)
robot-webserver (Pi #2, this repo) —TCP :5050→ ControlServer (link/server.py)
Xbox controller —evdev events→ GamepadReader (link/gamepad_handler.py)
GPS receiver —NMEA→ GPSReader (link/gps_reader.py)
↓ all three read/write the same shared state
RobotState (shared)
↔ every GPS fix, while in AUTO mode
Autopilot (link/autopilot.py) distance+heading → 2×PID → PWM
↓
MotorDriver (motor_control/motor_driver.py) → Motor GPIO

Since 2026-09-07, sending an RTE route and arming AUTO mode (MOD,AUTO from the console, or the controller's Y button — moved from A on 2026-09-12) really drives the robot: on every GPS fix, link/autopilot.py computes the heading/distance error to the current waypoint and feeds it through two PID loops to produce a motor command, advancing to the next point on arrival. Since 2026-09-12, the gamepad is listened to at all times and manual control always takes priority — touching a joystick immediately hands control back to manual, mid-route or not, and there is no more MOD button on /control (the site's console can still send MOD,AUTO/MOD,MANUAL by hand). Y refuses to arm AUTO if no target exists yet (no NAV point and no RTE route). Pressing B stops the robot, same as STP. Pressing START also stops the robot the same way, and then additionally powers off the Raspberry Pi itself (a real OS-level shutdown, not just the control scripts) — see the robot repo's README for the one-time sudo setup this needs. The "Distance + angle" button (also new on 2026-09-12, just above "STOP" on /control) is a second way to build a NAV frame — it fetches the robot's current position/heading first, then projects a distance and a rotation angle from there, entirely computed client-side on Pi #2; nothing changes here on Pi #1's side once that NAV frame arrives, it's handled exactly like one typed by hand. Known limitation, not hidden: there's no compass/IMU on this robot — the only heading source is the GPS receiver's own course-over-ground, which is only meaningful while actually moving, and the PID gains are only validated in offline simulation so far. DRV from the console, or the controller's sticks, still drive manually the same way as before.

Application files

Site core (repo root)

FileRole
app.py Main Flask application: all routes (/login, /control, /media, /power, /pages, /api/send, /api/power_history, /media/*), rendered as inline HTML (no templates/ folder) for /control and /media, or served as-is from pages/ for /power and the rest of pages/*.html. Handles session-based authentication, relays commands from the console to the robot via robot_link.send_command, proxies the live camera stream from camera/stream_server.py, and (2026-10-05) proxies/caches geotagged photo and video thumbnails (/media/thumb/<kind>/<filename>) and lists the robot's own on-board camera buffers as JSON (/media/robot_feed) for /media's "Robot camera" carousel. The /control page (status banner, two-tab Console/TCP console, command buttons, GPS map) is built entirely server-side then animated with JavaScript. It is the site's single entry point: the other modules are only ever loaded by it.
robot_link.py Minimal TCP client: opens a connection to link/server.py (Pi #1), sends a frame, reads a response line, closes. Used by app.py in the /api/send route, itself called by the console, the status banner's automatic polling, the GPS map's waypoint/route/media markers, and the /power page. Builds the frame via nmea.build_sentence and parses it via nmea.parse_sentence. Always returns a dictionary with at least ok and sent, never lets an exception propagate up to Flask.
nmea.py Builds and parses $PROV,...*hh frames: build_sentence, parse_sentence, XOR checksum computation. Exact copy of link/nmea.py from the robot repo, with no external dependency. Used only by robot_link.py. See the protocol page for the full format.
generate_password.py Script to run by hand (python3 generate_password.py) to obtain the value of WEBSERVER_PASSWORD_HASH. Prompts for the password twice at the keyboard (never displayed), hashes it with werkzeug.security.generate_password_hash, and prints the line to paste into .env. Not imported by any other file in the project; the plaintext password is never written to disk.
requirements.txt List of the site's Python dependencies: flask, python-dotenv, requests. Installed with pip install -r requirements.txt. Deliberately short — unlike the robot repo, this site has no hardware dependency (GPIO, camera, serial port).
.env / .env.example Runtime configuration, .env is never committed (credentials, session key) — .env.example serves as a commented template. Read at startup by app.py via load_dotenv(): site credentials, the robot's address/port (ROBOT_HOST/ROBOT_PORT) and its camera's (CAMERA_PORT/CAMERA_STREAM_PATH).
.gitignore Excludes .env (secrets), venv/ and Python caches (__pycache__/) from the Git repo. Has no effect at runtime, only at commit time.

Startup (systemd/)

Not imported by any Python file — a unit file read by systemd itself, installed by hand (see README.md, "Lancer le serveur au démarrage de la Pi").

FileRole
systemd/robot-webserver.service Starts app.py automatically at boot, as the robot user, once the network is up (2026-10-06). Same approach as the robot repo's own systemd/robot.service, adapted to this repo's single-process shape: app.py is the only thing to launch here (unlike Pi #1's link + camera pair), so ExecStart points directly at the project's venv's own python3 binary instead of needing a start_robot.sh-style wrapper script. Restarts automatically on crash (Restart=on-failure); logs go to the journal (journalctl -u robot-webserver.service -f).

Static pages (pages/)

Served as-is by app.py (route /pages/<file>, no templating) so their own HTML/CSS never breaks; they automatically appear in the /pages listing as soon as an .html file is dropped into this folder.

FileRole
protocole_controle.html Living reference for the robot's command protocol (proprietary NMEA $PROV,... frames): frame types, examples, checksum. Updated with every change to the protocol on the link/server.py side of the robot repo.
rapport_rover_dgps.html Standalone project report (network diagrams for both sites, the link/camera process layout, PID tuning). Rewritten 2026-10-06 to match the current architecture; maintained by hand again whenever it changes materially, same as this page.
architecture_webserver.html This page — dependency diagram and role of each file in robot-webserver. To be updated whenever a file is added to or removed from the repo.

Media content (media/)

The "Video feed"/"Images" panels these two folders feed moved from /control to their own /media page on 2026-10-05 (see _media_page() in app.py) — /control stays focused on driving the robot. A plain live-camera column came back to /control on 2026-10-06 (a middle column between Controls and Map), but it's unrelated to these two folders: it's just the robot's live MJPEG stream, same proxy (/media/camera) as /media's own "Video feed" panel, with no recorded-video fallback and nothing of its own stored on disk.

FolderRole
media/videos/ Videos (.mp4/.webm/.ogg/.mov) played one at a time in a loop in the "Video feed" panel of /media, only when the live camera stream is unavailable. Empty by default (just a .gitkeep) — shows a "coming soon" placeholder in that case.
media/images/ Images (.jpg/.jpeg/.png/.gif/.webp) shown as a slideshow (3s per image) in the "Images" panel of /media. Unrelated to the robot's own CAM,SNAP snapshots and recordings (see the protocol page), which stay on Pi #1's capped camera buffers and are surfaced separately — as the violet markers on /control's GPS map (via MED) and as the "Robot camera" carousel on /media (via /media/robot_feed, 2026-10-05) — this folder is a manual gallery, populated by hand, with no connection to either.
Outdoor mobile robot — page maintained by hand, alongside the site's code.
