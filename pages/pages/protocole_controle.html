Robot Control Protocol

Format of the messages exchanged between the website (Raspberry Pi #2) and the robot (Raspberry Pi #1). This page is updated whenever a new command is defined.

Who's in control: gamepad vs. website (updated 2026-09-12)

The gamepad plugged into Pi #1 is listened to continuously and MANUAL always wins by default: touching a stick takes control back immediately, even mid-AUTO drive (see the robot repo's link/gamepad_handler.py, robot_state_drive_handler()). Because of that, /control no longer has a mode-switch button — a physical operator never needs one to regain control, and MOD stays a valid sentence on the wire (still typeable in the console below) but isn't exposed as a quick-fill button anymore.

The controller's Y button re-arms AUTO mode (moved from A on this date) — but only if a target already exists (a NAV point sent from the site, or a GPS route uploaded via the "GPS Driving" button below); pressing it with neither set is a no-op. B is a full stop, same as STP. START also stops the robot, and additionally powers off the Raspberry Pi entirely (not just the control scripts) — see the robot repo's README for the one-time sudo setup this needs.

/control's buttons, top to bottom, are now: NAV, "GPS Driving", CAM, "Distance + angle" (new on this date — see the NAV row below), and "STOP" last so it never sits under a moving thumb. DRV, MOD, PID and STA no longer have dedicated buttons, but all four remain valid sentences, typeable directly in the console.

Why an NMEA-inspired protocol?

The project already uses NMEA 0183 to read the GPS (gps_parse.py), so reusing the same sentence style for robot control keeps a single read/write logic throughout the codebase instead of introducing a second one. A readable ASCII sentence can be read directly in the site's console (see the /control page) without any decoding tool, which helps a lot when debugging in the field. The comma-separated format is trivial to parse (split(",")), and the checksum provides a simple integrity check over a WiFi link that can be noisy.

Point of caution : NMEA was originally designed for one-way broadcasting (a sensor transmitting), not for command/response dialogue. The standard solution is to use proprietary NMEA sentences (P prefix + 3-letter code) and define your own command, acknowledgment, and error sentence types within them — this is the approach taken below.

Transport : TCP socket

Frames travel over a simple TCP connection between the two boards (Python's standard socket module, no external dependency) — chosen over MQTT (an extra broker to manage, overkill for 2 nodes) or plain HTTP (less suited to continuous telemetry). The robot (Pi #1) runs a TCP server (link/server.py in the robot repo, port 5050 by default) that accepts one frame per line and replies with an ACK/ERR/STA frame. The site (Pi #2) opens a connection, sends, reads one response line, closes — enough for commands typed by hand in the /control console.

Current status : STP and DRV update an in-memory state and respond correctly (ACK/ERR), but do not yet drive the real motors — motor_control/pwm.py is currently a blocking script that opens the GPIO at startup, not a callable function; actually wiring it up for real is the next step. NAV and PID record the received value (ACK) without acting on it yet (no link to the GPS/PID pipeline for now). RTE genuinely stores the waypoint list and genuinely advances target_lat/target_lon to the next one as the live GPS fix reaches each one in turn (same real logic as NAV's target, just chained automatically) — but, same caveat as NAV, nothing yet steers the motors to actually follow it. CAM,SNAP genuinely calls the GET /snap route of camera/stream_server.py (over local HTTP, separate process) and responds ACK/ERR depending on the result; CAM,REC_START and CAM,REC_STOP always respond ERR (video recording not implemented). In the STA response, the current position and cap/speed are genuinely read from a serial GPS receiver (link/gps_reader.py, untested on a real receiver — pynmea2/pyserial could not be installed in the environment where this module was written) and stay at 0 as long as no receiver is connected; the target position (target_lat/target_lon), however, does reflect the last NAV frame received, or the current waypoint of an active RTE route.

General sentence format

$PROV,TYPE,field1,field2,...*hh<CR><LF>
  • $PROV — fixed prefix (P = NMEA proprietary sentence, ROV = project code, 3 letters).
  • TYPE — 3-letter sentence identifier (DRV, NAV, STP...), see the table below.
  • subsequent fields, comma-separated, specific to each sentence type.
  • *hh — 2-character uppercase hexadecimal checksum, XOR of all bytes between $ and * (same calculation as standard NMEA sentences).
  • Evolution rule : only add fields at the end of a sentence (never in the middle), so that an older parser simply ignores the extra fields instead of crashing.

Defined sentences

REQ = site → robot (command)  •  RES = robot → site (response/telemetry)
Type Direction Fields Description Example
STP REQ — Emergency stop, highest priority: PWM of both motors set to 0 immediately. On /control, the "STOP" button (was labeled "STP" before 2026-09-12) sends this the instant it's clicked — no console step, unlike every other button below. $PROV,STP*60
DRV REQ left_pwm, right_pwm Direct manual control, bypasses the PID. PWM values between -255 and 255. No longer has its own quick-fill button on /control (2026-09-12) — still a valid sentence, type it in the console directly if needed; the gamepad's sticks call the equivalent of this straight into the robot's shared state without going over this wire protocol at all. $PROV,DRV,120,120*77
NAV REQ lat, N/S, lon, E/W Sets a single GPS waypoint to reach autonomously (the robot uses its existing distance/angle PID loops). lat/lon format identical to GPGGA sentences. Cancels any route in progress (see RTE below) — a manual NAV takes back control. Since 2026-09-12, the "Distance + angle" button on /control (second-to-last, just above "STOP") builds and sends one of these too: it reads the robot's current position and heading via a fresh STA request, computes a target bearing as current heading + the entered angle, projects the entered distance (meters) along that bearing from the current position, and sends the resulting point as a plain NAV — no new sentence type needed for it, this is just a second way to build the same one. The angle is deliberately relative to the robot's own cap (course over ground) rather than an absolute compass bearing; since there's no compass/IMU on this robot, cap only means anything while the robot is already moving — the button warns in the console when it's about to use a stale one (robot at a standstill) rather than silently computing a target from noise. $PROV,NAV,4807.038,N,01131.000,E*57
RTE REQ count, then count × (lat, N/S, lon, E/W) Sets an ordered list of GPS waypoints to follow automatically, one at a time — same per-point format as NAV, repeated count times. The robot heads for the first waypoint; once the live GPS fix is within ROUTE_ARRIVAL_RADIUS_M of it (5 m by default, overridable via that environment variable on Pi #1), it automatically advances to the next, and so on until the last one is reached. Replaces any previous route; a plain NAV or STP also cancels an active route. On /control, the "GPS Driving" button (was labeled "GPS route" before 2026-09-12) opens a file picker instead of prefilling the console — pick a plain text file with one point per line as lat,lon in decimal degrees (blank lines and lines starting with # are ignored), and the site converts it to this sentence and sends it. Capped at 200 waypoints per route. Either this or a plain NAV is what lets the gamepad's Y button re-arm AUTO (see the section above) — without one of the two, there's nothing for Y to drive toward. $PROV,RTE,2,4723.492,N,00044.340,W,4723.532,N,00044.292,W*6F
MOD REQ AUTO | MANUAL | IDLE Changes the operating mode: autonomous GPS tracking, manual control (DRV), or idle stop. No longer has its own button on /control (2026-09-12, see the section above) — the robot manages this itself now (gamepad priority, Y to re-arm AUTO); still a valid sentence for scripting/debugging from the console. $PROV,MOD,MANUAL*47
PID REQ D|A, kp, ki, kd Updates the PID coefficients of the Distance (D) or Angle (A) loop on the fly, without redeploying the code. No longer has its own quick-fill button on /control (2026-09-12) — still fully functional, type it in the console during a live test. $PROV,PID,D,1.0,0.0,0.5*04
CAM REQ SNAP | REC_START | REC_STOP Controls the onboard camera. SNAP: the robot (Pi #1) saves the current image to a local buffer folder (camera/tmp/, never more than 5 files — the oldest is deleted as soon as a 6th arrives), for later processing; independent of media/images/ on the site, which remains the static photo gallery. REC_START/REC_STOP: always ERR for now (see note above). The trigger goes through a local HTTP request to camera/stream_server.py (separate process), independent of the live video stream on /control, which uses its own HTTP connection. $PROV,CAM,SNAP*58
MED RES count, then count × (filename, kind, lat, N/S, lon, E/W, ts) Response to a $PROV,MED*hh request (no fields, 2026-10-05): the GPS position of every photo/video currently held in the robot's capped on-board buffers, for the violet markers on the /control map (see the section above). kind is SNAP or VID. Backed by the same small database on Pi #1 as the power history (see the Power page), but filtered down to only the files the camera process (camera/stream_server.py) is still actually holding (5 photos / 5 videos max, oldest rotated out first) — a row can outlive its file, and MED never reports one that's gone. Photos are geotagged at the moment of CAM,SNAP; videos are geotagged at the position when CAM,REC_START was sent, not wherever the robot ends up by CAM,REC_STOP (the file itself isn't named until the first frame is written, well after REC_START, so the start position is held in memory and only written to the database once REC_STOP hands back the real filename). Read-only, like STA below and RTE above — never changes robot state. On /control, hovering a violet marker lazily fetches the actual image/video from Pi #1 through the site's own thumbnail proxy, cached in a temp folder on Pi #2 that's cleared every time the page reloads; a hovered video shows a static first frame, it never autoplays. $PROV,MED,1,snap_1733.jpg,SNAP,4723.492,N,00044.340,W,1738765421*2C
STA RES lat, lat_dir, lon, lon_dir, cap, speed, left_pwm, right_pwm, battery, mode, target_lat, target_lat_dir, target_lon, target_lon_dir Response to a $PROV,STA*hh request (no fields): current telemetry and state, displayed in the status banner and the /control console. No longer has its own quick-fill button (2026-09-12) — it's still very much used, just automatically: the status bar polls it every few seconds on its own. Current position (lat/lat_dir/lon/lon_dir) and target position (target_lat/target_lat_dir/target_lon/target_lon_dir, last NAV frame received) use the same grouped format as NAV: value followed by hemisphere, side by side. Fields reordered on 2026-09-02 (a deliberate break from the previous format, since nothing relied on it yet) to fix a real bug: the two current-position fields originally had no hemisphere, so the site defaulted to assuming N/E — wrongly, since this robot operates west of the meridian. lat/lon/cap/speed are read from a serial GPS receiver by link/gps_reader.py (GPRMC/GGA sentences via pynmea2, same hardware as gps/gps_transfer.py) and stay at their fallback value of 0.0 as long as no receiver is connected or no valid sentence has been received. speed is in km/h, cap in degrees (course over ground, from GPRMC). battery stays at 0, there is no battery sensor in the project as of now. $PROV,STA,4723.462,N,00044.310,W,284.5,3.7,110,108,74,IDLE,4723.492,N,00044.340,W*7A
ACK RES type_commande Acknowledgment of a command received and accepted. $PROV,ACK,DRV*12
ERR RES code, message Command rejected or execution error (e.g. : invalid checksum, out-of-range value). $PROV,ERR,02,PWM_OUT_OF_RANGE*7D
To be defined later: reporting DGPS/RTK connection status, frame authentication code if the network becomes less reliable.

Checksum calculation

XOR of each character between $ and *, exclusive, expressed as 2-character uppercase hexadecimal (zero-padded if necessary):

def nmea_checksum(sentence_body: str) -> str: checksum = 0 for ch in sentence_body: checksum ^= ord(ch) return f"{checksum:02X}" # sentence_body = everything between $ and * (exclusive) # e.g.: nmea_checksum("PROV,STP") -> "60"
