Protocole de controle du robot

Format des messages echanges entre le site web (Raspberry Pi n2) et le robot (Raspberry Pi n1). Cette page est mise a jour a chaque nouvelle commande definie.

Pourquoi un protocole inspire de NMEA ?

Le projet utilise deja NMEA 0183 pour lire le GPS (gps_parse.py), donc reprendre le meme style de trame pour le controle du robot garde une seule logique de lecture/ecriture dans tout le code plutot que d'en introduire une deuxieme. Une trame ASCII lisible se lit directement dans la console du site (voir la page /control) sans outil de decodage, ce qui aide beaucoup pour deboguer sur le terrain. Le format virgule-separee est trivial a parser (split(",")), et la somme de controle (checksum) donne une verification simple de l'integrite sur une liaison WiFi qui peut etre bruitee.

Point d'attention : NMEA a ete concu a l'origine pour de la diffusion a sens unique (un capteur qui emet), pas pour du dialogue commande/reponse. La solution standard est d'utiliser les trames proprietaires NMEA (prefixe P + code sur 3 lettres) et d'y definir soi-meme des types de trames de commande, d'accuse de reception et d'erreur — c'est l'approche prise ci-dessous.

Transport : socket TCP

Les trames circulent sur une connexion TCP simple entre les deux cartes (module socket standard de Python, aucune dependance externe) — choisi plutot que MQTT (broker en plus a gerer, dispreportionne pour 2 noeuds) ou HTTP classique (moins adapte a de la telemetrie continue). Le robot (Pi n1) fait tourner un serveur TCP (link/server.py dans le depot robot, port 5050 par defaut) qui accepte une trame par ligne et repond par une trame ACK/ERR/STA. Le site (Pi n2) ouvre une connexion, envoie, lit une ligne de reponse, ferme — suffisant pour des commandes tapees a la main dans la console de /control.

Etat actuel : STP et DRV mettent a jour un etat en memoire et repondent correctement (ACK/ERR), mais ne pilotent pas encore les moteurs reels — motor_control/pwm.py est aujourd'hui un script bloquant qui ouvre le GPIO au demarrage, pas une fonction appelable ; le brancher pour de vrai est la prochaine etape. NAV et PID enregistrent la valeur recue (ACK) sans encore agir dessus (pas de lien avec le pipeline GPS/PID pour l'instant). CAM,SNAP appelle pour de vrai la route GET /snap de camera/stream_server.py (en HTTP local, processus separe) et repond ACK/ERR selon le resultat ; CAM,REC_START et CAM,REC_STOP repondent toujours ERR (enregistrement video non implemente). Dans la reponse STA, la position courante et cap/speed sont lus pour de vrai depuis un recepteur GPS serie (link/gps_reader.py, non teste sur un vrai recepteur — pynmea2/pyserial non installables dans l'environnement ou ce module a ete ecrit) et restent a 0 tant qu'aucun recepteur n'est branche ; la position cible (target_lat/target_lon), elle, reflete bien la derniere trame NAV recue.

Format general d'une trame

$PROV,TYPE,champ1,champ2,...*hh<CR><LF>
  • $PROV — prefixe fixe (P = trame proprietaire NMEA, ROV = code du projet, 3 lettres).
  • TYPE — identifiant de la trame sur 3 lettres (DRV, NAV, STP...), voir le tableau ci-dessous.
  • champs suivants separes par des virgules, specifiques a chaque type de trame.
  • *hh — checksum sur 2 caracteres hexadecimaux majuscules, XOR de tous les octets entre $ et * (calcul identique a celui des trames NMEA standard).
  • Regle d'evolution : ajouter des champs seulement en fin de trame (jamais au milieu), pour qu'un ancien parseur ignore simplement les champs en trop plutot que de planter.

Trames definies

REQ = site → robot (commande)  •  RES = robot → site (reponse/telemetrie)
Type Sens Champs Description Exemple
STP REQ — Arret d'urgence, priorite maximale : PWM des deux moteurs a 0 immediatement. $PROV,STP*60
DRV REQ left_pwm, right_pwm Pilotage manuel direct, court-circuite le PID. Valeurs PWM entre -255 et 255. $PROV,DRV,120,120*77
NAV REQ lat, N/S, lon, E/W Definit un point GPS a atteindre en autonome (le robot utilise ses PID distance/angle existants). Format lat/lon identique aux trames GPGGA. $PROV,NAV,4807.038,N,01131.000,E*57
MOD REQ AUTO | MANUAL | IDLE Change le mode de fonctionnement : suivi GPS autonome, pilotage manuel (DRV), ou arret au repos. $PROV,MOD,MANUAL*47
PID REQ D|A, kp, ki, kd Met a jour a chaud les coefficients PID de la boucle Distance (D) ou Angle (A), sans redeployer le code. $PROV,PID,D,1.0,0.0,0.5*04
CAM REQ SNAP | REC_START | REC_STOP Commande la camera embarquee. SNAP : le robot (Pi n1) sauvegarde l'image courante dans un dossier tampon local (camera/tmp/, jamais plus de 5 fichiers — le plus ancien est supprime des qu'un 6e arrive), pour un traitement ulterieur ; independant de media/images/ sur le site, qui reste la galerie de photos statiques. REC_START/REC_STOP : toujours ERR pour l'instant (voir note ci-dessus). Le declenchement passe par une requete HTTP locale vers camera/stream_server.py (processus separe), independamment du flux video en direct de /control, qui utilise sa propre connexion HTTP. $PROV,CAM,SNAP*58
STA RES lat, lat_dir, lon, lon_dir, cap, speed, left_pwm, right_pwm, batterie, mode, target_lat, target_lat_dir, target_lon, target_lon_dir Reponse a une requete $PROV,STA*hh (sans champs) : telemetrie et etat courants, affiches dans le bandeau de statut et la console de /control. Position courante (lat/lat_dir/lon/lon_dir) et position cible (target_lat/target_lat_dir/target_lon/target_lon_dir, derniere trame NAV recue) utilisent le meme format groupe que NAV : valeur puis hemisphere cote a cote. Champs reordonnes le 2026-09-02 (rupture assumee du format precedent, rien ne s'appuyait encore dessus) pour corriger un vrai bug : les deux champs de position courante n'avaient pas d'hemisphere au depart, le site supposait donc N/E par defaut — a tort, ce robot opere a l'ouest du meridien. lat/lon/cap/speed sont lus depuis un recepteur GPS serie par link/gps_reader.py (trames GPRMC/GGA via pynmea2, meme materiel que gps/gps_transfer.py) et restent a leur valeur de repli 0.0 tant qu'aucun recepteur n'est branche ou qu'aucune trame valide n'a ete recue. speed est en km/h, cap en degres (cap sur le sol, vient de GPRMC). batterie reste a 0, aucun capteur de batterie dans le projet a ce jour. $PROV,STA,4723.462,N,00044.310,W,284.5,3.7,110,108,74,IDLE,4723.492,N,00044.340,W*7A
ACK RES type_commande Accuse de reception d'une commande recue et acceptee. $PROV,ACK,DRV*12
ERR RES code, message Commande refusee ou erreur d'execution (ex : checksum invalide, valeur hors limites). $PROV,ERR,02,PWM_OUT_OF_RANGE*7D

Calcul du checksum

XOR de chaque caractere entre $ et *, exclus, exprime en hexadecimal majuscule sur 2 caracteres (complete par un zero si necessaire) :

def nmea_checksum(sentence_body: str) -> str: checksum = 0 for ch in sentence_body: checksum ^= ord(ch) return f"{checksum:02X}" # sentence_body = tout ce qui est entre $ et * (sans les inclure) # ex: nmea_checksum("PROV,STP") -> "60"
