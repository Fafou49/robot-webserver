Robot Control Protocol

Format of the messages exchanged between the website (Raspberry Pi #2) and the robot (Raspberry Pi #1). This page is updated whenever a new command is defined.

Who's in control: gamepad vs. website (updated 2026-09-18)

The gamepad plugged into Pi #1 is listened to continuously and MANUAL always wins by default: touching a stick takes control back immediately, even mid-AUTO drive (see the robot repo's link/gamepad_handler.py, robot_state_drive_handler()). Because of that, /control no longer has a mode-switch button — a physical operator never needs one to regain control, and MOD stays a valid sentence on the wire (still typeable in the console below) but isn't exposed as a quick-fill button anymore.

2026-09-18 remap of the right-hand button cluster (replaces the 2026-09-12 mapping below it): A (moved from Y) re-arms AUTO mode — but only if a target already exists (a NAV point sent from the site, or a GPS route uploaded via the "GPS Driving" button below); pressing it with neither set is a no-op. B now toggles video recording (CAM,REC_START/CAM,REC_STOP, genuinely implemented as of this date — see the CAM row below) instead of stopping the robot. X saves the robot's current GPS fix to a waypoint file on Pi #1. Y (moved from the unused slot left by X's old position) takes a camera snapshot (CAM,SNAP). START is unchanged: stops the robot, and additionally powers off the Raspberry Pi entirely (not just the control scripts) — see the robot repo's README for the one-time sudo setup this needs.

No more dedicated full-stop button on the gamepad since B now records video — a deliberate simplification on the robot side, not an oversight. Two safety nets remain: any stick movement immediately hands control back to MANUAL, and /control's own "STOP" button below still sends STP instantly. A dedicated gamepad stop button can be rebound to a free shoulder button on Pi #1 if wanted — see the robot repo's README.

/control's buttons, top to bottom, are: NAV, "GPS Driving", CAM, "Distance + angle", and "STOP" last so it never sits under a moving thumb. DRV, MOD, PID and STA no longer have dedicated buttons, but all four remain valid sentences, typeable directly in the console.

Why an NMEA-inspired protocol?

The project already uses NMEA 0183 to read the GPS (gps_parse.py), so reusing the same sentence style for robot control keeps a single read/write logic throughout the codebase instead of introducing a second one. A readable ASCII sentence can be read directly in the site's console (see the /control page) without any decoding tool, which helps a lot when debugging in the field. The comma-separated format is trivial to parse (split(",")), and the checksum provides a simple integrity check over a WiFi link that can be noisy.

Point of caution : NMEA was originally designed for one-way broadcasting (a sensor transmitting), not for command/response dialogue. The standard solution is to use proprietary NMEA sentences (P prefix + 3-letter code) and define your own command, acknowledgment, and error sentence types within them — this is the approach taken below.

Transport : TCP socket

Frames travel over a simple TCP connection between the two boards (Python's standard socket module, no external dependency) — chosen over MQTT (an extra broker to manage, overkill for 2 nodes) or plain HTTP (less suited to continuous telemetry). The robot (Pi #1) runs a TCP server (link/server.py in the robot repo, port 5050 by default) that accepts one frame per line and replies with an ACK/ERR/STA frame. The site (Pi #2) opens a connection, sends, reads one response line, closes — enough for commands typed by hand in the /control console.

Current status : STP and DRV update an in-memory state and respond correctly (ACK/ERR), but do not yet drive the real motors — motor_control/pwm.py is currently a blocking script that opens the GPIO at startup, not a callable function; actually wiring it up for real is the next step. NAV and PID record the received value (ACK) without acting on it yet (no link to the GPS/PID pipeline for now). RTE genuinely stores the waypoint list and genuinely advances target_lat/target_lon to the next one as the live GPS fix reaches each one in turn (same real logic as NAV's target, just chained automatically) — but, same caveat as NAV, nothing yet steers the motors to actually follow it. CAM,SNAP genuinely calls the GET /snap route of camera/stream_server.py (over local HTTP, separate process) and responds ACK/ERR depending on the result; CAM,REC_START and CAM,REC_STOP (genuinely implemented since 2026-09-18, see camera/recordings.py's VideoRecorder in the robot repo) call that same process's GET /rec/start / GET /rec/stop the same way. In the STA response, the current position and cap/speed are genuinely read from a serial GPS receiver (link/gps_reader.py, untested on a real receiver — pynmea2/pyserial could not be installed in the environment where this module was written) and stay at 0 as long as no receiver is connected; the target position (target_lat/target_lon), however, does reflect the last NAV frame received, or the current waypoint of an active RTE route. WPT and GRT (2026-09-19) are genuine, side-effect-free reads: WPT re-reads the robot's waypoints.txt file on every request, GRT returns whatever self.route currently holds in memory — both back the GPS map on /control (see the "Map" section below).

General sentence format

$PROV,TYPE,field1,field2,...*hh<CR><LF>
  • $PROV — fixed prefix (P = NMEA proprietary sentence, ROV = project code, 3 letters).
  • TYPE — 3-letter sentence identifier (DRV, NAV, STP...), see the table below.
  • subsequent fields, comma-separated, specific to each sentence type.
  • *hh — 2-character uppercase hexadecimal checksum, XOR of all bytes between $ and * (same calculation as standard NMEA sentences).
  • Evolution rule : only add fields at the end of a sentence (never in the middle), so that an older parser simply ignores the extra fields instead of crashing.

Defined sentences

REQ = site → robot (command)  •  RES = robot → site (response/telemetry)
Type Direction Fields Description Example
STP REQ — Emergency stop, highest priority: PWM of both motors set to 0 immediately. On /control, the "STOP" button (was labeled "STP" before 2026-09-12) sends this the instant it's clicked — no console step, unlike every other button below. $PROV,STP*60
SHD REQ — (2026-09-20) Emergency shutdown: stops both motors (same as STP) then powers off the Raspberry Pi — the exact same action the gamepad's BTN_START already triggers, just reachable from the website too. On /control, the red "Shutdown" button next to "STOP" sends this, but only after a confirmation prompt ("Are you sure?") — unlike STP, this is irreversible from the interface: nothing brings the Pi back on its own, someone has to physically power it back up. Requires passwordless sudo poweroff on the robot (see the robot repo's README, "Pilotage moteur et manette") — if that sudoers entry is missing, the robot's control scripts still stop, but the Pi itself stays on. $PROV,SHD*68
RBT REQ — (2026-09-20) Emergency reset: stops both motors (same as STP) then reboots the Raspberry Pi — SHD's twin, but the robot comes back online on its own after a while instead of staying off. No gamepad button is bound to this one, only the website. On /control, the "Reset" button next to "Shutdown" sends this, also behind a confirmation prompt. Requires the same passwordless-sudo setup as SHD, for sudo reboot instead. $PROV,RBT*73
DRV REQ left_pwm, right_pwm Direct manual control, bypasses the PID. PWM values between -255 and 255. No longer has its own quick-fill button on /control (2026-09-12) — still a valid sentence, type it in the console directly if needed; the gamepad's sticks call the equivalent of this straight into the robot's shared state without going over this wire protocol at all. $PROV,DRV,120,120*77
NAV REQ lat, N/S, lon, E/W Sets a single GPS waypoint to reach autonomously (the robot uses its existing distance/angle PID loops). lat/lon format identical to GPGGA sentences. Cancels any route in progress (see RTE below) — a manual NAV takes back control. Since 2026-09-12, the "Distance + angle" button on /control (second-to-last, just above "STOP") builds and sends one of these too: it reads the robot's current position and heading via a fresh STA request, computes a target bearing as current heading + the entered angle, projects the entered distance (meters) along that bearing from the current position, and sends the resulting point as a plain NAV — no new sentence type needed for it, this is just a second way to build the same one. The angle is deliberately relative to the robot's own cap (course over ground) rather than an absolute compass bearing; since there's no compass/IMU on this robot, cap only means anything while the robot is already moving — the button warns in the console when it's about to use a stale one (robot at a standstill) rather than silently computing a target from noise. $PROV,NAV,4807.038,N,01131.000,E*57
RTE REQ count, then count × (lat, N/S, lon, E/W) Sets an ordered list of GPS waypoints to follow automatically, one at a time — same per-point format as NAV, repeated count times. The robot heads for the first waypoint; once the live GPS fix is within ROUTE_ARRIVAL_RADIUS_M of it (5 m by default, overridable via that environment variable on Pi #1), it automatically advances to the next, and so on until the last one is reached. Replaces any previous route; a plain NAV or STP also cancels an active route. On /control, the "GPS Driving" button (was labeled "GPS route" before 2026-09-12) opens a file picker instead of prefilling the console — pick a plain text file with one point per line as lat,lon in decimal degrees (blank lines and lines starting with # are ignored), and the site converts it to this sentence and sends it. Capped at 200 waypoints per route. Either this or a plain NAV is what lets the gamepad's A button (moved from Y on 2026-09-18, see the section above) re-arm AUTO — without one of the two, there's nothing for A to drive toward. $PROV,RTE,2,4723.492,N,00044.340,W,4723.532,N,00044.292,W*6F
MOD REQ AUTO | MANUAL | IDLE Changes the operating mode: autonomous GPS tracking, manual control (DRV), or idle stop. No longer has its own button on /control (2026-09-12, see the section above) — the robot manages this itself now (gamepad priority, A to re-arm AUTO since the 2026-09-18 remap); still a valid sentence for scripting/debugging from the console. $PROV,MOD,MANUAL*47
PID REQ D|A, kp, ki, kd Updates the PID coefficients of the Distance (D) or Angle (A) loop on the fly, without redeploying the code. No longer has its own quick-fill button on /control (2026-09-12) — still fully functional, type it in the console during a live test. $PROV,PID,D,1.0,0.0,0.5*04
CAM REQ SNAP | REC_START | REC_STOP Controls the onboard camera. SNAP: the robot (Pi #1) saves the current image to a local buffer folder (camera/tmp/, never more than 5 files — the oldest is deleted as soon as a 6th arrives), for later processing; independent of media/images/ on the site, which remains the static photo gallery. REC_START/REC_STOP: genuinely implemented since 2026-09-18 — starts/stops writing the live feed to a video file in a similar capped buffer folder (camera/recordings/, never more than 5 files); also reachable from the gamepad's B button (see the section above), which toggles between the two based on whether a recording is currently running. Both SNAP and REC_START answer ERR cleanly if the camera isn't delivering frames yet (not plugged in, or not opened yet) rather than doing nothing silently. The trigger goes through a local HTTP request to camera/stream_server.py (separate process), independent of the live video stream on /control, which uses its own HTTP connection. $PROV,CAM,SNAP*58
STA RES lat, lat_dir, lon, lon_dir, cap, speed, left_pwm, right_pwm, battery, mode, target_lat, target_lat_dir, target_lon, target_lon_dir, dgps, route_index Response to a $PROV,STA*hh request (no fields): current telemetry and state, displayed in the status banner and the /control console. No longer has its own quick-fill button (2026-09-12) — it's still very much used, just automatically: the status bar is refilled every few seconds from the same shared poll as the GPS map (see the "Map" section below), rather than requesting STA on its own schedule. Current position (lat/lat_dir/lon/lon_dir) and target position (target_lat/target_lat_dir/target_lon/target_lon_dir, last NAV frame received) use the same grouped format as NAV: value followed by hemisphere, side by side. Fields reordered on 2026-09-02 (a deliberate break from the previous format, since nothing relied on it yet) to fix a real bug: the two current-position fields originally had no hemisphere, so the site defaulted to assuming N/E — wrongly, since this robot operates west of the meridian. lat/lon/cap/speed are read from a serial GPS receiver by link/gps_reader.py (GPRMC/GGA sentences via pynmea2, same hardware as gps/gps_transfer.py) and stay at their fallback value of 0.0 as long as no receiver is connected or no valid sentence has been received. speed is in km/h, cap in degrees (course over ground, from GPRMC). battery stays at 0, there is no battery sensor in the project as of now. dgps (new field, 2026-09-19, extend-only): DGPS once a GGA sentence has reported a differentially-corrected fix, GPS once one has reported an uncorrected fix, UNKNOWN before any GGA quality indicator has been seen at all (no receiver attached, RMC-only sentences so far, or no fix yet) — shown as a small badge next to the current-position value on /control, always visible ("DGPS: Active" in green/bold only while the value is exactly DGPS, "DGPS: Inactive" otherwise, since 2026-09-19). mode (shown on /control since 2026-09-20, the field itself already existed): MANUAL/AUTO/IDLE, displayed right next to the DGPS badge — amber/bold for AUTO (the robot may be steering itself), blue for MANUAL, muted for IDLE. route_index (new trailing field, 2026-09-20, extend-only): how many points of the currently active "GPS Driving" route have already been reached (0 with no active route). Used by /control's map to color an already-reached route point red instead of yellow and to split the route's connecting segment into an "already driven" (red) and "still to drive" (yellow) pair that meet exactly at the robot's own live position — see the "Map" section below. $PROV,STA,4723.462,N,00044.310,W,284.5,3.7,110,108,74,IDLE,4723.492,N,00044.340,W,DGPS,2*48
WPT REQ (none) Request (2026-09-19, no fields): asks for the list of waypoints saved on the robot via the gamepad's X button (see RobotState.save_waypoint()/list_waypoints(), robot repo). Feeds the blue markers on /control's GPS map (see /api/map_data below). $PROV,WPT*hh
WPT RES count, [lat, lat_dir, lon, lon_dir, timestamp] × count Response to WPT: a count field followed by count points, 5 fields each (was 4, extended 2026-09-20: timestamp is the save-time RobotState.save_waypoint() already wrote to the waypoints file, round-tripped so /control's map can show when each waypoint was actually saved — empty if that line has none, e.g. hand-edited or saved before this field existed). Coordinates are converted to ddmm.mmmm along the way since the robot's own waypoints file stores plain decimal degrees. count is 0 as long as no waypoint has been saved. GRT below keeps its own, unchanged 4-fields-per-point shape — a route has no "saved" date of its own. $PROV,WPT,1,4723.500,N,00044.400,W,2026-09-20T08:14:03*hh
GRT REQ (none) Request (2026-09-19, no fields): asks for the route currently active on the robot (the last RTE received, i.e. the "GPS Driving" button on /control) via RobotState.get_route() (robot repo). Feeds the yellow markers on /control's GPS map. $PROV,GRT*hh
GRT RES count, [lat, lat_dir, lon, lon_dir] × count Response to GRT: same 4-fields-per-point format as RTE (unlike WPT above, no timestamp field here — a route has no "saved" date of its own, just whatever was last uploaded). Already in ddmm.mmmm on the robot side (the route is stored as received), so returned without conversion. count is 0 as long as no RTE has been sent, or after a STP/NAV that canceled it. $PROV,GRT,0*hh
WPD REQ index (2026-09-20) Deletes one saved waypoint by its 0-based index — the same order WPT returns them in, i.e. the "Waypoint N" numbering on /control's map, N−1. Rewrites the waypoints file on the robot with just that line removed (comments/blank/malformed lines are preserved untouched, see RobotState.delete_waypoint(), robot repo). Answers ERR,16,WPD_INDEX_OUT_OF_RANGE:<index> for an index that doesn't exist, including on a missing/empty file. Triggered from /control's map by right-clicking a blue waypoint marker and confirming the prompt. $PROV,WPD,0*68
RTD REQ index (2026-09-20) Deletes one point from the currently active "GPS Driving" route by its 0-based index — the same order GRT returns them in. Unlike re-sending a shorter RTE, this does not reset driving progress: RobotState.delete_route_point() (robot repo) edits the in-memory route in place and shifts the current-target index down only when the deleted point was already passed or was the current target itself, so an in-progress route is never restarted or sent backward. Answers ERR,16,RTD_INDEX_OUT_OF_RANGE:<index> for an index outside the current route. Triggered from /control's map by right-clicking a yellow/red "GPS Driving" marker and confirming the prompt. $PROV,RTD,1*68
ACK RES type_commande Acknowledgment of a command received and accepted. $PROV,ACK,DRV*12
ERR RES code, message Command rejected or execution error (e.g. : invalid checksum, out-of-range value). $PROV,ERR,02,PWM_OUT_OF_RANGE*7D
To be defined later: reporting DGPS/RTK connection status, frame authentication code if the network becomes less reliable.

Map (2026-09-19, reworked 2026-09-20)

The rightmost panel of /control, which used to show a photo slideshow (media/images/), now shows an offline GPS plan — a point cloud projected in meters, not a real tiled basemap (this site has no external/CDN dependency today, and the robot operates in the field where an Internet uplink on Pi #2 isn't guaranteed). Rendered on a light background (unlike the rest of this dark-themed page) so it reads like a paper map. Four point layers, one color per source :

  • Green — the robot's current position (STA, already existed).
  • Blue — waypoints saved via the gamepad's X button (new WPT request, see the table above).
  • Yellow — the "GPS Driving" route currently active on the robot (new GRT request).
  • Red — history of NAV commands sent from this site. The robot itself keeps no history at all (STA only ever reports the current target) — so the site (Pi #2) logs every successfully-sent NAV to a local file (data/nav_history.txt, same lat,lon,timestamp shape as the robot's own waypoints.txt).

A GET /api/map_data route (unlike /api/send, read-only and available to viewer accounts too) queries the robot (STA, WPT, GRT) and re-reads the local history on every call; the page's <canvas> and its status bar both poll it together, every 3 seconds.

Refresh rate and network traffic (2026-09-19): the poll interval was raised from 5 s to 3 s at the same time the status bar's own, previously separate 3 s STA poll (a plain /api/send call) was folded into this single route — /api/map_data's JSON now also carries the raw STA fields (sta_ok/sta_fields) the status bar needs. Net effect: STA is now queried once per 3 s poll instead of twice per (roughly) 3 s and 5 s on two uncoordinated schedules — a lower combined rate than before, despite the nominal refresh getting faster. WPT and GRT (waypoints and the active route) change only when the operator explicitly acts — saving a gamepad waypoint, sending a new route — so the site now caches both for 10 s server-side instead of re-querying the robot every poll; the map still shows a fresh position every 3 s regardless, since STA itself is never cached. This matters because robot_link.send_command() opens a brand-new TCP connection per command (no persistent link), and the robot's TCP server spawns one thread per connection — on a Raspberry Pi already doing real-time motor control, GPS reading and gamepad reading, avoiding needless connection churn matters more than shaving another second or two off the display refresh, which a rover moving at a few km/h (a few meters per 3 s) wouldn't visibly benefit from anyway.

Fixed origin, manual zoom, auto-dezoom (2026-09-20): the map's projection center is set once, from the bounding box of whatever points are known the first time it renders, and never recentered afterward — only the zoom level (and, since the fix below, a pan offset) changes. The mouse wheel zooms in/out manually. If the robot's live position would otherwise drift outside the currently visible area, the map automatically zooms out just enough to keep it in view (it never zooms back in on its own once that happens — only a further wheel zoom or a page reload restores a closer view).

Wheel zoom fix (2026-09-20): two bugs in the wheel zoom above, reported as "often stuck at maximum zoom, and doesn't zoom onto points properly": (1) every wheel event used to apply the same fixed ×1.15 step regardless of how much was actually scrolled — fine for a discrete mouse notch, but a trackpad's momentum scroll fires many small-deltaY events per swipe, so that step compounded 30-40 times in under a second and slammed the zoom into its maximum (or minimum) almost instantly. deltaY is now normalized and clamped per event, so the zoom speed tracks how much was actually scrolled. (2) zooming used to always scale around the fixed projection center, so a point away from that center just moved further off-screen as you zoomed in on it — there was no way to zoom in on a point away from the middle of the view. The wheel now zooms toward the cursor instead (Google-Maps-style: whichever point is under the mouse stays under the mouse), via a small pixel-space pan offset layered on top of the fixed origin. That pan is discarded (reset to center) whenever the auto-dezoom safety net above fires, since keeping the robot visible always takes priority over a manual pan/zoom the operator made while looking elsewhere.

Click-to-navigate (2026-09-20): clicking any colored point on the map — a waypoint (blue), a "GPS Driving" route point (yellow), or a past NAV-history dot (red) — sends a plain NAV straight to that point's real GPS coordinates, exactly as if it had been typed into the console or built by the "Distance + angle" panel. The cursor turns into a pointer over any clickable point so this is discoverable without reading this page. The robot's own live marker (green) is not clickable this way — it's already there. No confirmation prompt, same as every other driving command on this page (STOP, "Distance + angle"...) — only Shutdown/Reset ask first, since those are the only irreversible ones. Disabled for a viewer/guest session, same restriction as every other command besides STA (see VIEWER_ALLOWED_COMMANDS in /api/send's own docstring) — the cursor stays a plain arrow there instead of a pointer, and clicking does nothing client-side rather than round-tripping to a 403.

Waypoint segments and hover tooltip (2026-09-20): the blue waypoint markers are now joined 1→2→3→…→N by a thin line in the same blue, in the order WPT returns them (their save order on the robot) — a plan sketch, not a bold graphic element. NAV history (red) is deliberately left as separate scatter points, not joined this way — it's a log of past one-off commands, not a single ordered plan. The route (yellow/red) is also joined, but as a two-color chain rather than this simple single-color one — see "Route progress, robot splice and right-click delete" below. Hovering any marker shows a small tooltip with its label, GPS coordinates, and — where one actually exists — a date/time: the real save-timestamp for waypoints (WPT's new timestamp field, see the table above) and for NAV history (already logged locally), and the last successful poll's time for the robot's own live marker (it has no "saved" date of its own, being a live snapshot of where it is right now). The route has no such date and its tooltip shows coordinates only. The tooltip's left border always matches the hovered marker's own resolved color — important once a route point can be red instead of yellow, see below.

Route progress, robot splice and right-click delete (2026-09-20): the "GPS Driving" route is now joined in order too, but split into two colored chains at the robot's own live position rather than one plain line — red ("already driven") from the route's start through every already-reached point up to the robot, then yellow ("still to drive") from the robot onward through every point still ahead. The robot's projected position is the exact point shared by both chains, so they always meet cleanly with no gap or overlap regardless of how far along the route the robot currently is. Each already-reached route point's marker itself also turns red (the same color as a NAV-history dot) instead of yellow. This is driven by STA's new route_index field (see the table above) and applies to the route only, not to waypoints — waypoints have no equivalent "how far along" signal to key this off of, so their own segment (above) stays a plain single-color line. Falls back to one plain yellow line, exactly as before this feature, whenever there's no live robot fix to split on.

Right-clicking any colored point on the map — except the robot's own live marker — now offers to delete it from wherever it's actually stored, after a plain confirmation dialog (same "ask before an irreversible action" pattern as Shutdown/Reset): a waypoint sends WPD,<index> to the robot, a "GPS Driving" route point (whether still yellow or already turned red) sends RTD,<index>, and a NAV-history dot is removed from this site's own local log via POST /api/nav_history/delete (matched by its exact GPS coordinates and save-timestamp, since that log is capped to the most recent 500 points and a plain list index into it wouldn't stay a stable identifier). A successful WPD/RTD immediately invalidates this site's own 10 s WPT/GRT cache (see the refresh-rate paragraph above) so the deleted point doesn't linger on the map, and either action is followed by an immediate extra poll rather than waiting for the next scheduled one. Disabled for a viewer/guest session client-side (no context-menu prompt at all), and independently rejected server-side too — WPD/RTD aren't in VIEWER_ALLOWED_COMMANDS, and /api/nav_history/delete checks the session role itself.

Media page (2026-09-19)

A new /media page, linked from /control's top nav, shows four panels in a 2×2 grid : the live camera feed (top-left, same /media/camera proxy /control's own video panel already uses), the robot's video recordings (top-right — the CAM,REC_START/CAM,REC_STOP buffer, camera/recordings/ on the robot, never more than 5 files), this site's own manually-dropped photo gallery (bottom-left, media/images/ — unchanged, same files /media/images/<file> already served), and the robot's Snap picture (bottom-right — the CAM,SNAP buffer, camera/tmp/ on the robot, never more than 5 files).

Until now, neither the Snap-photo buffer nor the recordings buffer was reachable off the robot at all — only the actions that fill them (CAM,SNAP/CAM,REC_START/CAM,REC_STOP, see the CAM row above) and the live feed itself. camera/stream_server.py (robot repo) now also answers GET /snapshots and GET /recordings (a JSON listing of filenames, newest first) and GET /snapshots/<file>/GET /recordings/<file> (the raw file bytes, a plain JPEG or MP4) — a requested filename is checked against the store's own current listing before being served, so a stale (already pruned — both buffers keep at most 5 files) or made-up name gets a clean 404, never a path-traversal read. This site proxies all four the same way /media/camera already proxies the live stream (/media/snapshots, /media/snapshots/<file>, /media/recordings, /media/recordings/<file>), so the robot's camera server never needs to be reachable directly from a browser — everything stays behind this site's login. The recordings and Snap-photo panels poll their listing every 10 s (same buffers can change at any time from the gamepad or the console); the photo gallery is rendered once, from the server, since it only changes when a file is manually dropped into media/images/ — a page reload already picks that up.

Recordings panel: one video at a time, filling the panel, and playable in the browser (2026-09-21): the recordings panel used to render every file in the buffer as its own small figure/thumbnail (same grid layout as the Snap-photo panel), which meant several <video> elements could in principle play at once. It's now a single <video id="recordingPlayer"> that fills the whole panel box (same absolute-fill technique already used by /control's live camera feed — position: absolute; inset: 0; width/height: 100%; object-fit: contain) and plays the buffer's files back-to-back in order, automatically moving to the next one on the <video>'s own ended event and wrapping back to the first after the last — the exact same single-player/playlist pattern /control's own video panel already uses, just adapted to a list that can change underneath it. The 10 s poll diffs the freshly-fetched file list against what's currently known and leaves the player alone when nothing changed, so playback is never restarted or interrupted by a poll that found the same 5 files; when the list does change (a new recording, or the oldest one aged out of the 5-file buffer), it keeps playing the same file if it's still present (just at its new position in the list) and only resets to the first file if the one currently playing was the one pruned away. If the current file fails to load (error event — e.g. a stale/corrupted file), it's skipped to the next one after a short delay, guarded so that several error events firing for the same failure only ever trigger one skip.

Why the 2 recorded videos wouldn't play at all, and the fix (2026-09-21): unrelated to the panel layout above, the actual files were the problem — camera/recordings.py's VideoRecorder was writing with the mp4v FourCC (MPEG-4 Part 2), which no mainstream browser can decode in a <video> element even though the .mp4 file itself is valid (VLC/ffplay open it fine). Fixed on the robot repo side (see its own README, "Vidéos enregistrées illisibles dans un navigateur"): the writer now prefers an H.264 FourCC when the Pi's OpenCV build supports it, and falls back to transcoding the file to H.264 with the system ffmpeg right after recording stops if it doesn't. The 2 videos already on the robot were recorded before this fix and are still in the old, browser-incompatible mp4v format — they need to be re-recorded (or manually transcoded with ffmpeg -i old.mp4 -c:v libx264 -pix_fmt yuv420p new.mp4 directly on the robot) to actually play here; only recordings made after this update is deployed will play automatically. Separately, both camera/stream_server.py and this site's /media/recordings/<file>//media/snapshots/<file> proxy routes now forward the browser's Range header upstream and relay the real 200/206/416 response back (previously always 200, full file) — required by Safari/iOS to play video at all, and also what lets the player seek within a video instead of only playing it start-to-finish.

Checksum calculation

XOR of each character between $ and *, exclusive, expressed as 2-character uppercase hexadecimal (zero-padded if necessary):

def nmea_checksum(sentence_body: str) -> str: checksum = 0 for ch in sentence_body: checksum ^= ord(ch) return f"{checksum:02X}" # sentence_body = everything between $ and * (exclusive) # e.g.: nmea_checksum("PROV,STP") -> "60"
