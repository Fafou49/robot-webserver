Robot Control Protocol

Format of the messages exchanged between the website (Raspberry Pi #2) and the robot (Raspberry Pi #1). This page is updated whenever a new command is defined.

Who's in control: gamepad vs. website (updated 2026-09-12)

The gamepad plugged into Pi #1 is listened to continuously and MANUAL always wins by default: touching a stick takes control back immediately, even mid-AUTO drive (see the robot repo's link/gamepad_handler.py, robot_state_drive_handler()). Because of that, /control no longer has a mode-switch button — a physical operator never needs one to regain control, and MOD stays a valid sentence on the wire (still typeable in the console below) but isn't exposed as a quick-fill button anymore.

The controller's Y button re-arms AUTO mode (moved from A on this date) — but only if a target already exists (a NAV point sent from the site, or a GPS route uploaded via the "GPS Driving" button below); pressing it with neither set is a no-op. B is a full stop, same as STP. START also stops the robot, and additionally powers off the Raspberry Pi entirely (not just the control scripts) — see the robot repo's README for the one-time sudo setup this needs.

/control's buttons, top to bottom, are now: NAV, "GPS Driving", CAM, "Distance + angle" (new on this date — see the NAV row below), and "STOP" last so it never sits under a moving thumb. DRV, MOD, PID and STA no longer have dedicated buttons, but all four remain valid sentences, typeable directly in the console.

Why an NMEA-inspired protocol?

The project already uses NMEA 0183 to read the GPS (gps_parse.py), so reusing the same sentence style for robot control keeps a single read/write logic throughout the codebase instead of introducing a second one. A readable ASCII sentence can be read directly in the site's console (see the /control page) without any decoding tool, which helps a lot when debugging in the field. The comma-separated format is trivial to parse (split(",")), and the checksum provides a simple integrity check over a WiFi link that can be noisy.

Point of caution : NMEA was originally designed for one-way broadcasting (a sensor transmitting), not for command/response dialogue. The standard solution is to use proprietary NMEA sentences (P prefix + 3-letter code) and define your own command, acknowledgment, and error sentence types within them — this is the approach taken below.

Transport : TCP socket

Frames travel over a simple TCP connection between the two boards (Python's standard socket module, no external dependency) — chosen over MQTT (an extra broker to manage, overkill for 2 nodes) or plain HTTP (less suited to continuous telemetry). The robot (Pi #1) runs a TCP server (link/server.py in the robot repo, port 5050 by default) that accepts one frame per line and replies with an ACK/ERR/STA frame. The site (Pi #2) opens a connection, sends, reads one response line, closes — enough for commands typed by hand in the /control console.

Current status : STP and DRV update an in-memory state and respond correctly (ACK/ERR), but do not yet drive the real motors — motor_control/pwm.py is currently a blocking script that opens the GPIO at startup, not a callable function; actually wiring it up for real is the next step. NAV and PID record the received value (ACK) without acting on it yet (no link to the GPS/PID pipeline for now). RTE genuinely stores the waypoint list and genuinely advances target_lat/target_lon to the next one as the live GPS fix reaches each one in turn (same real logic as NAV's target, just chained automatically) — but, same caveat as NAV, nothing yet steers the motors to actually follow it. CAM,SNAP genuinely calls the GET /snap route of camera/stream_server.py (over local HTTP, separate process) and responds ACK/ERR depending on the result; CAM,REC_START and CAM,REC_STOP always respond ERR (video recording not implemented). In the STA response, the current position and cap/speed are genuinely read from a serial GPS receiver (link/gps_reader.py, untested on a real receiver — pynmea2/pyserial could not be installed in the environment where this module was written) and stay at 0 as long as no receiver is connected; the target position (target_lat/target_lon), however, does reflect the last NAV frame received, or the current waypoint of an active RTE route.

Transport #2 : LoRa radio link (added 2026-10-24)

A second, independent transport for the exact same sentences above: an E22-900T22U LoRa module, one per Pi, wired over USB-serial and run in "transparent transmission" mode — once its air frequency / network address / air data rate are configured once (a one-time step with the module's own AT-command or config-GUI tool), the two modules behave like a slow, lossy serial cable between the boards. Because it's just another byte pipe carrying the same $PROV,...*hh sentences through the same dispatch table (link/server.py's _handle_sentence(), shared verbatim by both transports), every sentence type documented on this page already works over LoRa with zero changes — nothing above this section is LoRa-specific.

Why add it at all: WiFi has a hard range limit, and this robot operates outdoors, away from any access point, by design. app.py's _send_command_with_fallback() tries the radio link first for ordinary console commands, falling back to WiFi/TCP automatically — a deliberate "keep both up while the radio link is being tuned" choice, not a hard cutover. The one exception is the new DGPS correction relay below, which does the opposite (WiFi first, LoRa only as a fallback) for its own reasons — see that section.

UART baud rate vs. air data rate — not the same number. LORA_BAUD_RATE (9600 by default) is only the speed between the Pi's USB port and the module itself — raising it does not extend range or increase how fast bytes actually cross the air. The module's own air data rate (configured separately, in the module's own config mode) is what the air actually carries, and it's a direct range/speed trade-off: a lower air rate reaches further for the same transmit power. LORA_AIR_RATE_BYTES_PER_S on Pi #1 must always be kept in sync with whatever the module is actually set to (air rate in kbps × 1000 ÷ 8) — it's what the budget below is built around, and a mismatch either throttles the robot below what the link could really carry, or lets it push more than the link can carry, garbling traffic.

Field finding, 2026-10-24: at the module's 2.4 kbps factory default (≈300 B/s), the DGPS correction relay alone was already saturating the link, leaving no room for ordinary telemetry commands — not just the automatic image fallback. Both Pi's dongles are accordingly being raised to 9.6 kbps (≈1200 B/s, ×4) and their UART speed to 19200 (so the Pi‎↔dongle USB-serial link isn't itself the new bottleneck — at 9600 baud it caps out around 960 B/s, just under the new 1200 B/s air rate), accepting shorter range in exchange. See tools/lora_configure.py (present in both repos) for the reconfiguration procedure — it talks to the module's own configuration registers directly over the same USB-serial port (the module has no GPIO M0/M1 pins on this USB dongle variant; its configuration mode is entered with a physical side button, not from software). Update LORA_BAUD_RATE on both Pis and LORA_AIR_RATE_BYTES_PER_S on Pi #1 (see each repo's .env.example) to match once both dongles are confirmed reconfigured.

Two frame kinds share one wire. The text sentences on this page ($PROV,...*hh\r\n) and a new compact binary framing for image chunks (link/binary_frame.py, identical module copied into both repos) coexist on the exact same serial stream. A reader distinguishes them with a single peeked byte: every binary frame starts with a fixed MAGIC byte (0xA5), which can never be mistaken for $ (0x24), the first byte of every text sentence — so one cheap check is enough to dispatch each incoming unit to the right parser, no ambiguity possible. Each binary frame's 13-byte header (magic, type, image id, sequence number, total chunk count, payload length, CRC32) is self-describing, so a chunk can be decoded (or recognized as corrupted, via its own CRC32) independently of any other.

LoRa radio budget & priority — "DGPS always wins"

Whatever the module's air capacity actually is (LORA_AIR_RATE_BYTES_PER_S, see above — 300 B/s at the module's 2.4 kbps factory default, 1200 B/s at the 9.6 kbps both dongles are being raised to as of 2026-10-24), it's shared by everything riding the LoRa link, and real-world multi-constellation RTCM correction streams (what the DGPS relay below carries) have been measured at roughly 290–560 bytes/second on their own — comparable to, and sometimes already bigger than, the old 300 B/s channel (this is exactly the saturation the 2026-10-24 field finding above was about), but a comfortably smaller fraction of the new 1200 B/s one. Explicit decision (2026-10-24, asked and confirmed): when DGPS corrections and an in-progress image transmission would otherwise compete for the same saturated channel, DGPS corrections always win, whatever the current air rate. Image transmission is allowed to be slow, stall, or make no progress for a while when the channel is busy — that's the accepted, intentional consequence, not a bug — the air rate increase makes it less likely to happen often, not impossible.

The mechanism is a simple token bucket (LoraLinkBudget in link/lora_image_streamer.py, refilled continuously at the air rate above, drawn down by every byte either Pi actually writes to the port). DGPS correction sentences (COR) and every protocol reply (ACK/ERR/STA/...) are written immediately, unconditionally — never checked against the bucket first. Only an automatic image chunk is explicitly gated: it's only sent if the bucket currently holds enough bytes for it, and simply waits for the next opportunity otherwise. The priority falls out of that asymmetry by construction, with no explicit "if DGPS is active, pause images" coupling needed anywhere in the code.

  • DGPS corrections (COR) ~30% · ~350 B/s
  • Automatic image chunks ~68% · ~830 B/s
  • Protocol replies / ACKs ~2% · ~20 B/s

DGPS correction relay (COR, added 2026-10-24)

Pi #1 used to fetch its own DGPS/RTK corrections directly from an NTRIP caster (gps/dgps_transfer.py, now retired) — which silently produced nothing whenever Pi #1 itself had no internet on site, exactly the situation the LoRa link exists for. Corrections are now fetched by Pi #2 instead (dgps_relay.py, robot-webserver repo — it has the reliable connection) and relayed to Pi #1 as a new COR sentence, one base64-encoded batch per second. Pi #1 writes the decoded bytes straight to the GPS receiver's own serial port (link/dgps_injector.py) and reports back how many bytes actually got written.

Transport choice for COR is the opposite of ordinary commands: WiFi is tried first, LoRa only once every WiFi candidate has failed to even connect. Corrections don't need the scarce radio budget at all when WiFi can carry them for free, so this keeps that budget available for the image fallback below — LoRa only has to carry corrections during exactly the scenario this whole feature is for (Pi #1 out of WiFi range). A batch too big for one sentence (a real burst can run bigger than comfortable) is simply split across several COR sentences rather than ever being truncated.

No encryption on this relay for now (explicit decision, 2026-10-24) — see the note at the end of this page.

Automatic camera snapshot over LoRa (added 2026-10-24)

While Pi #1 has no WiFi reachable and the robot is actively driving (mode MANUAL or AUTO — never while IDLE), it repeatedly grabs a small image from the camera, transmits it over LoRa, and loops: capture → transmit → display whatever has arrived so far → once complete, hold the finished image on screen for 3 seconds → capture again. Shown live on both /control's Camera panel and /media's Video feed panel on the website, with an explicit "receiving.../transfer complete" badge.

Inspired by how deep-space probes stream pictures home over a far slower, far less reliable link than this one (NASA's Deep Space Network / ESA's Estrack): images are encoded as progressive JPEG, so a still-incomplete transfer already renders a usable (just blurrier) picture instead of nothing at all — the same idea as the ICER compression used on Mars rovers. Missing chunks are tracked by Pi #2 and recovered with selective retransmission (an IMGNAK listing exactly which chunk numbers are still missing, inspired by CCSDS CFDP's file-transfer protocol for deep-space links) — never the whole image resent for one bad chunk. Pi #2 sends a single IMGACK once it has every chunk, letting Pi #1 move straight to the 3-second hold instead of waiting out a timeout for nothing.

Deliberately kept separate from the robot's own photos: this automatic snap is captured through its own endpoint (GET /snap_transient on camera/stream_server.py, small — 160×120, grayscale, quality 40 by default — to fit this link's budget), is never written to Pi #1's capped snapshot store, and never counts as (or pushes out) a user-requested CAM,SNAP. No encryption on this link for now either — see the note below.

New sentences added alongside this work (2026-10-24) — travel over whichever transport is currently in use (WiFi/TCP or LoRa, same shared dispatch table as every other sentence on this page); same REQ/RES convention.

General sentence format

$PROV,TYPE,field1,field2,...*hh<CR><LF>
  • $PROV — fixed prefix (P = NMEA proprietary sentence, ROV = project code, 3 letters).
  • TYPE — 3-letter sentence identifier (DRV, NAV, STP...), see the table below.
  • subsequent fields, comma-separated, specific to each sentence type.
  • *hh — 2-character uppercase hexadecimal checksum, XOR of all bytes between $ and * (same calculation as standard NMEA sentences).
  • Evolution rule : only add fields at the end of a sentence (never in the middle), so that an older parser simply ignores the extra fields instead of crashing.

Defined sentences

REQ = site → robot (command)  •  RES = robot → site (response/telemetry)

STP REQ — Emergency stop, highest priority: PWM of both motors set to 0 immediately. On /control, the "STOP" button (was labeled "STP" before 2026-09-12) sends this the instant it's clicked — no console step, unlike every other button below. $PROV,STP*60
SHD REQ — Shuts down Pi #1 entirely (not just the control scripts) — explicit user request, 2026-10-12. Calls the exact same ControlServer._shutdown_pi() the gamepad's START button already used (see the robot repo's README, "Pilotage moteur et manette"), so no second shutdown mechanism exists. On /control, the "Shutdown Pi #1" button directly below "STOP" sends this — unlike every other button here, it asks for confirmation first (window.confirm) since, unlike STP, this can't be undone by just driving again. Not in VIEWER_ALLOWED_COMMANDS (app.py), so a read-only "guest" account is rejected with FORBIDDEN_READ_ONLY_ACCOUNT if it's ever sent directly to /api/send — moot in practice, since that account's /control page never renders the Controls panel (and its buttons) at all. $PROV,SHD*68
DRV REQ left_pwm, right_pwm Direct manual control, bypasses the PID. PWM values between -255 and 255. No longer has its own quick-fill button on /control (2026-09-12) — still a valid sentence, type it in the console directly if needed; the gamepad's sticks call the equivalent of this straight into the robot's shared state without going over this wire protocol at all. $PROV,DRV,120,120*77
NAV REQ lat, N/S, lon, E/W Sets a single GPS waypoint to reach autonomously (the robot uses its existing distance/angle PID loops). lat/lon format identical to GPGGA sentences. Cancels any route in progress (see RTE below) — a manual NAV takes back control. Since 2026-09-12, the "Distance + angle" button on /control (second-to-last, just above "STOP") builds and sends one of these too: it reads the robot's current position and heading via a fresh STA request, computes a target bearing as current heading + the entered angle, projects the entered distance (meters) along that bearing from the current position, and sends the resulting point as a plain NAV — no new sentence type needed for it, this is just a second way to build the same one. The angle is deliberately relative to the robot's own cap (course over ground) rather than an absolute compass bearing; since there's no compass/IMU on this robot, cap only means anything while the robot is already moving — the button warns in the console when it's about to use a stale one (robot at a standstill) rather than silently computing a target from noise. Format note (2026-10-07): typing a point in plain decimal degrees here (e.g. copied from the status bar's own "current"/"target" display just below, which is decimal degrees) used to be accepted silently and decoded as a wildly wrong point — the console now auto-detects and converts that case client-side before sending (see app.py's normalizeGpsCommand), and link/robot_state.py itself now rejects anything that still doesn't look like a genuine ddmm.mmmm latitude with ERR,22 (NAV_LAT_LON_IMPLAUSIBLE) as a safety net for anything that talks to the robot directly. $PROV,NAV,4807.038,N,01131.000,E*57
RTE REQ count, then count × (lat, N/S, lon, E/W) Sets an ordered list of GPS waypoints to follow automatically, one at a time — same per-point format as NAV, repeated count times. The robot heads for the first waypoint; once the live GPS fix is within ROUTE_ARRIVAL_RADIUS_M of it (5 m by default, overridable via that environment variable on Pi #1), it automatically advances to the next, and so on until the last one is reached. Replaces any previous route; a plain NAV or STP also cancels an active route. On /control, the "GPS Driving" button (was labeled "GPS route" before 2026-09-12) opens a file picker instead of prefilling the console — pick a plain text file with one point per line as lat,lon in decimal degrees (blank lines and lines starting with # are ignored), and the site converts it to this sentence and sends it, so this format-mismatch note doesn't apply to it. Capped at 200 waypoints per route. Either this or a plain NAV is what lets the gamepad's Y button re-arm AUTO (see the section above) — without one of the two, there's nothing for Y to drive toward. Format note (2026-10-07): same decimal-degrees auto-detection and plausibility check as NAV above applies per point if this is typed into the console by hand — an implausible point raises ERR,13 (RTE_LAT_LON_IMPLAUSIBLE) with the offending point's index. $PROV,RTE,2,4723.492,N,00044.340,W,4723.532,N,00044.292,W*6F
WPT RES count, then count × (lat, N/S, lon, E/W) Response to a $PROV,WPT*hh request (no fields, 2026-09-19): every waypoint saved so far via the gamepad's X button (waypoints/waypoints.txt on the robot), for the blue markers on the /control GPS map. Same "count then count × 4 fields" shape as RTE's own request and GRT's response below, so the site reuses one parser for all three — unlike GRT, the decimal-degree coordinates stored on disk are converted to this protocol's ddmm.mmmm + direction format fresh on every request, since the file itself holds plain decimal pairs. Read-only, like MED/STA — never changes robot state. Index 0 is the oldest saved waypoint; WPD below deletes by that same index. $PROV,WPT,2,4723.492,N,00044.340,W,4723.532,N,00044.292,W*7F
WPD REQ index Deletes one saved waypoint (2026-10-05) — index is 0-based, same order the WPT query above reports them in. Backs the right-click "delete this point" on a blue marker on /control's GPS map. By index rather than by resending the lat/lon: round-tripping a coordinate back to the exact text already on disk in waypoints/waypoints.txt risks a rounding mismatch that would silently miss the line; the index sidesteps that entirely. Every other line in the file (comments, blank lines, anything that fails to parse) is left untouched. ERR,18 (WAYPOINT_INDEX_OUT_OF_RANGE) if that index doesn't exist right now. $PROV,WPD,2*6A
GRT RES count, then count × (lat, N/S, lon, E/W), then route_index, RETURN|DRIVE Response to a $PROV,GRT*hh request (no fields, 2026-09-19): the currently active route — the last RTE upload ("GPS Driving"), or an in-progress return-to-waypoints run — for one of the red markers on the /control map (the map's colour scheme groups an uploaded route and a waypoint-return together, since from the map's point of view both are just "a line the robot is currently following"). Each point is already stored pre-encoded as (lat, N/S, lon, E/W) exactly like RTE's own fields, so this just flattens the stored route back out — no decimal/NMEA conversion happens here, unlike WPT above. The full route is always reported, including points already behind the robot, so the map's markers and RTD's indices stay unaffected. Empty (count 0, no point fields, route_index 0, mode DRIVE) once no route has been sent yet, or right after STP/a fresh NAV clears it. Read-only, never changes robot state. Two trailing fields (2026-10-07, extend-only — an older client that doesn't know about them yet simply ignores them, same convention as STA's DGPS field and PWR's cpu_temp field): route_index is 0-based, how far into the point list above the robot already is (route[route_index:] is what's actually left to drive — the points before that are already behind it but still listed here); the last field is RETURN for a waypoint return (BTN_A, retracing waypoints.txt) or DRIVE for an ordinary RTE upload. Both come from a single atomic read on the robot so they can never describe two different routes. Backs the real-distance progress bar shown under the status bar on /control while a route is active — it colours/labels itself blue/"Waypoint return (BTN_A)" or red/"GPS driving route" from the mode field, and spaces the remaining points by actual cumulative GPS distance (not by count) using the robot's live position and speed (from STA) to also show a per-point ETA. $PROV,GRT,2,4723.492,N,00044.340,W,4723.532,N,00044.292,W,0,DRIVE*11 (ordinary GPS Driving route, not yet advanced)
$PROV,GRT,2,4723.492,N,00044.340,W,4723.532,N,00044.292,W,1,RETURN*56 (waypoint return, first point already reached)
RTD REQ index Deletes one point of the currently active route (2026-10-06) — index is 0-based, same order GRT above reports it in. Backs the right-click "delete this point" on a red marker on /control's GPS map — the last of the three marker colours (blue/violet/red) to get one; the map's other red marker, the single ad-hoc "NAV sent" point, has no backing store on the robot at all, so the site simply forgets it locally instead of sending anything here. Unlike WPD (a plain text file, untouched by any in-flight driving decision), this edits live navigation state: deleting a point already behind the robot shifts the route's internal position counter down by one so it keeps naming the same upcoming leg; deleting the point currently being chased moves the target on to whatever is now at that same position (or leaves it on the just-deleted point's own coordinates if the route is now empty, same "done" convention as a route finishing on its own); deleting a point further ahead changes nothing else. Never touches waypoints.txt on disk, even when the active route is a waypoint-return (BTN_A) — only WPD edits that file. ERR,10 (RTD_NEEDS_1_FIELD) if the field count is wrong; ERR,21 (ROUTE_INDEX_OUT_OF_RANGE) if that index doesn't exist right now (already passed, already deleted by a concurrent request, or the route was replaced/cleared in the meantime). $PROV,RTD,1*68
MOD REQ AUTO | MANUAL | IDLE Changes the operating mode: autonomous GPS tracking, manual control (DRV), or idle stop. No longer has its own button on /control (2026-09-12, see the section above) — the robot manages this itself now (gamepad priority, Y to re-arm AUTO); still a valid sentence for scripting/debugging from the console. $PROV,MOD,MANUAL*47

CAM REQ SNAP | REC_START | REC_STOP Controls the onboard camera. SNAP: the robot (Pi #1) saves the current image to a local buffer folder (camera/tmp/, never more than 5 files — the oldest is deleted as soon as a 6th arrives), for later processing; independent of media/images/ on the site, which remains the static photo gallery. REC_START/REC_STOP: always ERR for now (see note above). MED RES count, then count × (filename, kind, lat, N/S, lon, E/W, ts) Response to a $PROV,MED*hh request (no fields, 2026-10-05): the GPS position of every photo/video currently held in the robot's capped on-board buffers, for the violet markers on the /control map (see the section above). kind is SNAP or VID. Backed by the same small database on Pi #1 as the power history (see the Power page), but filtered down to only the files the camera process (camera/stream_server.py) is still actually holding (5 photos / 5 videos max, oldest rotated out first) — a row can outlive its file, and MED never reports one that's gone. Read-only, like STA below and RTE above — never changes robot state. On /control, hovering a violet marker lazily fetches the actual image/video from Pi #1 through the site's own thumbnail proxy, cached in a temp folder on Pi #2 that's cleared every time the page reloads; a hovered video shows a static first frame, it never autoplays. $PROV,MED,1,snap_1733.jpg,SNAP,4723.492,N,00044.340,W,1738765421*6D
MDD REQ filename, SNAP|VID Deletes one photo/video (2026-10-05) — identified by its exact MED filename and kind. Backs the right-click "delete this point" on a violet marker on /control's GPS map (the site only sends this after the user confirms a popup, since unlike WPD above this also removes the underlying file, not just an entry in a list). Removes the file from the camera process's own capped store (new DELETE /snapshots/<filename> or DELETE /recordings/<filename> on camera/stream_server.py) AND its geotag row in the database, best-effort regardless of which succeeds. ERR,20 (MEDIA_NOT_FOUND) if the camera process says that file wasn't there (already rotated out by the normal 5-file cap, or already deleted) — the database row is still cleaned up in that case. ERR,12 (CAMERA_UNAVAILABLE, same code CAM uses) if the camera process can't be reached at all — the database row is deliberately left alone then, since the file might still genuinely exist. STA RES lat, lat_dir, lon, lon_dir, cap, speed, left_pwm, right_pwm, battery, mode, target_lat, target_lat_dir, target_lon, target_lon_dir, dgps Response to a $PROV,STA*hh request (no fields): current telemetry and state, displayed in the status banner and the /control console. The grid itself comes from a background survey: while driving (gamepad or AUTO), the robot buffers one (timestamp, position, PV power) sample to a local file every time it has moved at least 5 metres since the last one — gated on an actually valid GPS fix (always true by construction, nothing to measure distance against otherwise) and on PWR's own available flag being true (same gating HIS already uses, so a disconnected Tracer cable never pairs a real position with a placeholder reading). Checksum calculation

XOR of each character between $ and *, exclusive, expressed as 2-character uppercase hexadecimal (zero-padded if necessary):

def nmea_checksum(sentence_body: str) -> str: checksum = 0 for ch in sentence_body: checksum ^= ord(ch) return f"{checksum:02X}" # sentence_body = everything between $ and * (exclusive) # e.g.: nmea_checksum("PROV,STP") -> "60"

A note on security (LoRa link, as of 2026-10-24)

Nothing on the LoRa link is encrypted yet — explicit decision for this first pass ("dans un premier temps on n'encrypte pas"): not the text sentences, not the DGPS correction payloads, not the image chunks. The E22 module's own hardware KEY-register scrambling was evaluated and deliberately set aside (a 16-bit keyspace, a proprietary/unaudited algorithm, no replay protection — weak enough that it wouldn't meaningfully raise the bar). A software layer (e.g. AES-GCM/ChaCha20-Poly1305 over each sentence/chunk) remains the planned next step once this first unencrypted version has been exercised in the field; see the "to be defined later" row in the sentence table above.
